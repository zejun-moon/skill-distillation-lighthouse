# 脱敏规范

> **适用对象**：任何要发布到公网（GitHub / Gitee / 博客 / 分享链接）的
> 代码、文档、报告、截图、日志片段。
>
> 一句话原则：**公开仓 = 全网可检索 = 会被爬。**
> 你无法预知谁会搜到、搜到后会不会拿去做别的事，所以**默认全部脱敏**，
> 只保留「让内容成立」所必需的信息。

---

## 1. 威胁模型：什么东西会泄露

按「泄露后能造成什么后果」排序，**后果越重越要严格**：

| 类别 | 例子 | 后果 |
|---|---|---|
| **凭据** | 口令、token、私钥、AK/SK、cookie、证书 | 直接被接管 |
| **内网地址与域名** | `*.test.local`、`10.x.x.x`、`harbor.<内网域名>` | 内网探测、钓鱼入口 |
| **私有仓库地址** | `harbor.<内网域名>/team/app:tag` | 暴露内部制品结构与命名 |
| **账号与身份** | 用户名、工号、邮箱、真实姓名 | 定向社工、撞库 |
| **内部资源标识** | K8s namespace、uid、集群名、数据库名 | 拼出内部架构 |
| **内部流程与组织信息** | 「我们 3 个废仓待删」「某客户环境」 | 声誉与合规风险 |
| **业务数据** | 客户名、订单量、真实域名 | 商业秘密 |
| **文件与路径线索** | `/root/<用户名>/...`、`backup-<内部代号>-<日期>` | 拼出主机角色与流程 |
| **截图与日志片段** | 终端输出里带 IP / token / 客户名 | **最容易漏，且最容易被忽略** |

> ⚠️ **截图是最容易出事的一类。** 终端回显、浏览器书签栏、聊天窗口、监控面板
> —— 里面常常同时藏着 IP、域名、账号和时间线。贴之前逐个放大看。

## 2. 逐类替换表（照着替换，不要临场发挥）

| 原始形态 | ❌ 不要写 | ✅ 写成 | 说明 |
|---|---|---|---|
| 真实 IP | `192.168.2.31` | `10.0.0.x` | **用 `.x` 占位**，别用 `10.0.0.1`——后者看着像真的 <!-- scan: allow —— 本行是"反例"示范，刻意保留真值形态 -->
| 端口组合 | `192.168.2.31:3000` | `10.0.0.x:3000` | 端口可保留（本身不敏感） <!-- scan: allow —— 同上 -->
| 内网域名 | `grafana.test.com` | `grafana.example.com` | **保留域名结构**，只换主域 <!-- scan: allow —— 同上 -->
| 带个人前缀的通配域名 | `<个人前缀>.*.petclinic.test.local` | `*.petclinic.example.com` | 前缀要去掉 <!-- scan: allow —— 同上 |
| 带个人前缀的 namespace | `<个人前缀>-spring-petclinic-microservices` | `spring-petclinic-microservices` | **去掉前缀**，保留业务语义 |
| 容器/Pod 名 | `vets-service-6c4cc85f55-zh526` | `vets-service-<hash>` | |
| Grafana uid | `d461de83-2d17-4839-...` | `$DS_UID` | **参数化**，别留真 uid <!-- scan: allow —— 同上 |
| 文件夹 uid | `cf908328-8b3f-4d8f-...` | `$FOLDER_UID` | 同上 <!-- scan: allow —— 同上 -->
| 私有镜像地址 | `harbor.corp/team/app:5.0.1` | `registry.example.com/team/app:5.0.1` | **保留 tag**，那是版本信息，有价值 <!-- scan: allow —— 同上 |
| 内网 GitLab | `git@gitlab.corp:team/repo.git` | `git@gitlab.example.com:team/repo.git` | <!-- scan: allow —— 同上 -->
| 内部账号名 | `<内部账号>` | `<user>` / `service-account` | |
| 口令 / token | `P@ssw0rd!` / `ghp_xxx` | `<token>` / `$TOKEN` | **绝不写"假得像真的"** |
| 邮箱 | `<姓名拼音>@corp.cn` | `user@example.com` | |
| 真实姓名 | `<姓名>` | 「维护者」「该服务负责人」 | 角色化 |
| 带用户名的家目录路径 | `/root/<用户名>/backup/` | `/opt/app/` 或 `<workspace>/` | |
| 备份目录名 | `backup-<内部代号>-2026-11-12` | `backup-<env>-<date>` | |
| 工单 / 文档 ID | `627709240` | `TBD` | |
| 主机角色 | 「跳板机 <角色代号> <真实 IP>」 | 「运维跳板机」 | 角色可留，地址要脱 |

> ⚠️ **这份表本身也不能出现真实标识。**
> 如果「脱敏规范」里写着要脱敏的具体账号名，那规范文档就是泄露源。
> → 规范里只写**形态**（"带个人前缀的 namespace"），把真值留给扫描规则（规则文件自带豁免标记）。

### 替换表的判定原则

- **保留「可复现性」，去掉「可定位性」**
  - 版本号 `5.0.1`、端口 `8080`、指标名 `http_server_requests_seconds_count`
    → **保留**（没有它们内容就不成立）
  - 哪个 IP、哪个 uid、哪个域名 → **去掉**（有替代方案，不影响内容成立）
- **占位符必须一眼看出是占位符**
  - ✅ `10.0.0.x`、`<token>`、`example.com`、`$DS_UID`
  - ❌ `10.0.0.1`（像真的）、`abc123`（像真 token） <!-- scan: allow —— 本行是"反例"示范 -->
- **同一份材料里占位符要一致**
  - 别一会儿 `10.0.0.x` 一会儿 `192.168.1.1` <!-- scan: allow —— 本行是"反例"示范 -->

## 3. 七条硬规则

1. **默认全部脱敏**，不要"我记得这个无所谓"——判断标准是**后果**，不是你的感觉
2. **宁多勿少**：不确定要不要脱 → 脱。删掉一段真实信息通常不影响内容成立
3. **示例统一用保留域**：`example.com` / `example.org` / `10.0.0.x` / `<token>`
4. **真实凭据**（哪怕是测试环境的）**一律替换**——测试凭据往往是真凭据
5. **截图贴前逐行放大看**：终端输出、浏览器地址栏、标签页标题
6. **不写"脱敏后的示例"来替代真跑一遍**：示例必须来自真实执行，只是换了标识符
7. **机器扫描 + 人工复核**两道都要做：
   - 机器能抓格式化的泄漏（IP、token、uuid、邮箱）
   - 机器抓不到「这句话本身就泄露了内部情况」（见 §7）

## 4. 豁免机制：允许有例外，但必须显式

真实内容里总有些"不得不写"的东西（比如某个官方文档里引用的示例 IP）。
**不要偷偷留，要显式豁免并写清理由**：

```
10.20.30.40  # check_repo: allow —— 官方文档原样引用，用于说明保留网段含义
```

规则：

- 豁免**逐行**生效，不是一个文件级开关
- 必须**写明理由**，否则下一个维护者会当成"忘了脱"
- 豁免数量应该**很少**；如果超过 10 处，说明规则过严，该改规则而不是加豁免

## 5. 机器门禁：为什么不能只靠人眼

真实案例（本规范自己的开发过程）：

| 现象 | 说明 |
|---|---|
| 扫描器把**自己的规则定义**也扫了出来 | 规则文件里写着被禁的关键词 → 自指误报 |
| 扫描器把**测试样本**也扫了出来 | 测试里要写"真的 IP"来验证扫描器 → 又自指 |
| 扫描器对**真实 ServiceMonitor 清单命中 0 处** | 规则只覆盖了 IP/域名，**漏了内部 ns 前缀** → 规则过窄 |

前两个是**误报**（让人失去对工具的信任），第三个是**漏报**（比误报危险得多）。

### 三条工程纪律

1. **改规则必须同时改测试**，补**阳性**样本（必须命中）+ **阴性**样本（不得误报）
2. **测试样本在运行时拼接**，源码里不出现完整字面量
   ```python
   # ✅ 源码里没有完整 token 字面量 —— 机器扫描器和 gitleaks 都不会误报
   FAKE_IP = "192.168." + "2.31"
   FAKE_TOKEN = "gh" + "p_" + "abcdefghijklmnopqrstuvwxyz0123"
   ```
   > 否则：gitleaks 会把假 token 当真密钥，CI 直接红；自研扫描器也会自指误报。
3. **每次改规则跑阳性对照**：拿**未脱敏**的真实素材喂扫描器
   → 命中 0 = 扫描器是摆设，必须修

### 扫描器至少要覆盖

- IPv4（**校验八位组 ≤255**，否则版本号 `999.999.999.999` 会被误判）
- 内网域名（`.test.local` / `.test.com` / `.internal` / 私有仓库前缀）
- 私有镜像仓库地址
- 凭据（私钥块 / `AKIA` / `ghp_` / `github_pat_` / `glpat-` / 明文 `password:` 赋值 / Bearer token）
- 内部资源 uuid（仪表盘/文件夹 uid 一律参数化）
- 邮箱（占位邮箱要放行）
- 个人标识（内部前缀、真实姓名）

> **规则宁严勿松**：误报可以豁免，漏报没人会发现。

## 6. 提交前检查清单

```bash
# ① 机器扫描（必须 0 命中）
python3 tools/check_repo.py

# ② 阳性对照（确认扫描器有牙）
python3 tools/check_repo.py < 未脱敏的真实文件   # 应报出问题

# ③ 人工复核（机器抓不到的）
grep -rn "内部\|待删\|废仓\|客户\|我们公司" --include='*.md' .
```

**人工复核要看什么**（机器永远抓不到的部分）：

- [ ] 有没有暴露**组织结构**：「3 个仓待删」「某项目组」「总部/分支」
- [ ] 有没有暴露**内部流程与时间线**：备份目录名、故障发生日期与规模
- [ ] 有没有暴露**业务信息**：客户名、订单量、真实业务域名
- [ ] 有没有暴露**人的痕迹**：姓名、工号、值班表、聊天记录截图
- [ ] 文档里说的**结论**是否恰好泄露了内部实现的敏感细节

## 7. 机器抓不到的三类「语义性泄露」

这是脱敏最容易漏的部分——**格式完全合规，内容却泄露**：

| 类型 | 例子 | 为什么危险 |
|---|---|---|
| **规模与拓扑** | 「12 个 deployment 全单副本 + 几乎无 requests/limits」 | 直接告诉别人这套环境很脆 |
| **弱点自曝** | 「Grafana 的 SQLite 在 NFS 上 → 改文件夹名会死锁」 | 精确暴露了一个可被利用的缺陷 |
| **组织与流程** | 「GitLab 无 API token，3 个废仓删不掉」 | 暴露内部权限与运维状态 |

**处理方式**：这类内容要**抽象一层**再写——

- 「12 个 deployment 全单副本 + 几乎无 requests/limits」
  → 「该演练环境**全部单副本**、几乎没有 requests/limits」
- 「Grafana 的 SQLite 在 NFS 上 → 改文件夹名会死锁」
  → 「**Grafana 的数据库放在网络存储上时**，改文件夹标题会死锁」
- 「GitLab 无 API token，3 个废仓删不掉」
  → 「部分内部仓因**缺少凭据**无法清理」

> 抽象的原则：**保留技术结论，去掉可定位的规模数字与组织细节**。
> 技术内容对读者的价值恰恰在于结论，而不在于"我们这儿有 12 个"。

## 8. 泄露之后：不是改代码就完了

发现已经推到公网的内容含敏感信息，**按这个顺序**做：

1. **先轮换凭据**（如果泄露的是凭据）—— 改代码不撤销已经泄露的凭据
2. **再清理内容** —— 改文件 / 删文件
3. **再处理历史** —— 公开仓的 git 历史里还留着；需要重写历史或让平台清理
4. **评估影响** —— 这个信息公开了多久、是否已被爬取
5. **沉淀规则** —— 把这个坑写进扫描器规则，让它**下次**能被自动抓到

> ⚠️ **只改当前文件是不够的。** 公开仓的 `git log` 里每一版都在，
> 爬虫早就把历史版本拉走了。所以第 1 步（轮换凭据）优先级最高。

---

## 9. 什么时候可以不用脱敏

- **纯公开数据**：官方文档、公开仓库、公共 IP 段、开源项目原样引用
- **本身就是公开的**：README 里的项目名、公开 demo 地址
- **用户明确说不敏感且确认过后果** —— 但这需要**记录下来**（谁确认的、为什么）

**默认假设是"要脱敏"。** 例外要显式、要有记录。
