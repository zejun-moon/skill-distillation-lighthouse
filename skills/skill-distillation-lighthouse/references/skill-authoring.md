# 技能写作规范

> 目标：让 AI **能自己判断该不该加载这个技能**、**加载后知道第一步做什么**、
> **每一步都知道做完怎么验**。

---

## 1. frontmatter：这是 AI 的路由依据

```yaml
---
name: skill-distillation-lighthouse     # 必须 == 目录名（自检会验）
license: MIT
description: <中英双语 + 触发词枚举，≤ 1024 字符>
---
```

只有三个字段是必需的。**`description` 是唯一决定 AI 会不会加载它的东西**，
写得再好的正文，description 没写对等于不存在。

### description 的写法：三个要素

**① 说清这个技能干什么**

> ✅ 「把一次真实的运维/开发实战沉淀成 AI 可直接加载调用的技能仓」
> ❌ 「本技能包含脱敏规范、写作规范和扫描脚本」——这是目录，不是触发条件

**② 枚举触发场景（最重要）**

> ✅ 「凡是用户提到『把经验沉淀成技能』『写一个 skill』『做脱敏』『敏感信息扫描』…等场景，都要用本技能」

用**用户真会打出来的词**，不是你的术语。写完自检一遍：
「用户如果遇到这个问题，会不会搜到这句话里的某个词？」

**③ 写同义说法**

用户不会说你的术语，他会描述症状：

> ✅ 「即使用户没说『脱敏』而只说『发布到 GitHub 会不会泄露内网信息』」
> ✅ 「即使用户没说『监控』而只说『看不到服务的运行状况』」

**④ 中英双语**（团队里有两种语言提问时都能命中）

> ✅ 「Distill real operations experience into AI-loadable skill repositories: ...」

### 长度：≤ 1024 字符

超了会被自检拦下。**别删触发词来省长度**——把说明部分压简洁，把触发词写全。

---

## 2. 正文结构：只回答四个问题

```markdown
# <一句话说清这个技能解决什么>

<一段话：这是从哪次真实实战沉淀下来的，覆盖什么>

## 什么时候不要用本技能
<什么时候它不适用 —— 这一节最容易被跳过，但最影响 AI 的判断质量>

## 第 0 步 · <先确认前提>
<主流程：每步都有「做什么 + 做完怎么验」>

## 第 N 步 · ...

## 排障入口
<出错了去哪个 reference 查 —— 一张「现象 → 去哪」表>

## 边界：这些动作一律先问用户
<会改变业务行为 / 不可逆的动作>

## 配套文件
<每个文件一句话说明>
```

### 「什么时候不要用」为什么必写

AI 拿不准时，默认会**倾向于用**一个看起来相关的技能。
明确写出会导致误用的场景，AI 才能在边界处停下来问你。

> ✅ 「业务里是 Go / Node 服务 → 用对应语言的 exporter，不要强上 actuator」
> ✅ 「只是临时故障、很快会变的配置 → 写事故记录，不进技能仓」

---

## 3. 每一步都要有「通过条件」

这是技能仓和知识库最核心的差别。

❌ 知识库写法：「配置 actuator 端点」
✅ 技能写法：

```bash
# 验证端点真的出指标（三态判定）
bash scripts/verify-actuator-endpoint.sh --url http://<svc>.<ns>:8080/actuator/prometheus
```

好的「通过条件」是**可执行的**：一条命令 + 一个明确的成功输出。
让 AI 能自己判断「这步做完没有」，而不是回头问你。

### 排障入口用表

```markdown
| 现象 | 先看 | 大概率原因 |
|---|---|---|
| target 数 = 0，但对象存在 | `pitfalls.md` #1 | 缺 `release` 标签 |
| target up 但查不到序列 | `pitfalls.md` #2 #7 | 抓到假阳性 200 / 服务没装 registry |
```

「现象」要写成**用户能认出来的样子**（值班时看到的就是这个）。

---

## 4. 正文 < 500 行：拆分原则

`SKILL.md` 只放**主流程 + 判断标准 + 排障入口 + 边界**。其余一律进 `references/`。

| 内容 | 去处 |
|---|---|
| 主流程、判断标准、排障入口、边界 | `SKILL.md` |
| 坑的完整清单 | `references/pitfalls.md` |
| 某个子领域的详细配方 | `references/<topic>.md` |
| 可执行脚本 | `scripts/` |
| 原始实战记录 | `field-reports/` |

> **超过 500 行就该拆**，不是"写得详细"，是"该拆了"。
> 拆分标准：**主流程能不能在 5 分钟内读完并知道下一步做什么**。

引用路径要在 SKILL.md 里写全（`references/xxx.md`），自检会验**每个被引用的路径都真实存在**——
写错了 AI 会照着不存在的文件找。

---

## 5. 内容的四要素：结论 + 判据 + 可复现动作 + 失败样本

每条结论都要能回答四个问题：

| 要素 | 问题 | 反例 |
|---|---|---|
| **结论** | 是什么 | 「ServiceMonitor 要加标签」 |
| **判据** | 怎么确认是这个原因 | ❌ 缺失 → 只说结论，AI 无法自查 |
| **可复现动作** | 具体怎么做 | ❌ 「按文档配一下」 |
| **失败样本** | 当时怎么判断错的 | ❌ 缺失 → 下次还会踩同一个坑 |

**失败样本是最值钱、也最常被省略的。** 写法：

```markdown
### 现象：面板明明有数据，Y 轴却冒出 noValue 文案
- **第一反应**：怀疑数据源断了
- **对照实验**：同一查询、只改一个参数逐个截图
  | decimals | noValue | 结果 |
  |---|---|---|
  | 无 | 有 | ✅ 干净 |
  | `0` | 有 | ❌ 文案漏进 Y 轴 |
- **根因**：`decimals` 是整数时，字符串型 `noValue` 被当成额外数值类别混进刻度
- **处理**：时序图面板一律不设 `decimals`
```

---

## 6. 诚实标注验证状态

每条内容标一个等级，**别把推测写成结论**：

| 标记 | 含义 | 要求 |
|---|---|---|
| ✅ | **实测确认** | 真的跑过，能说出复现步骤和观察到的输出 |
| 📄 | **推断** | 据源码 / 官方文档 / 推理得出，**没实测** |
| 未测 | 没验证过 | 明确写出来，别混在正文里 |

> 写「实测」却不给复现步骤 = 没实测。
> 写「据 X 源码确认」时**给出文件路径与行号**，让读者能自己核。

---

## 7. 边界声明：把危险动作交给人

技能会指导 AI 去操作真实系统。**有些动作会改变业务行为**，必须写成
「向用户确认」，而不是自动执行：

```markdown
## 边界：这些动作一律先问用户

- **重建业务镜像**（加依赖）→ 影响发布链路
- **management.endpoints.web.exposure.include: '*'** → 会同时暴露 env/threaddump/sbom
- **删除远端资源**（仓库、文件、目录）
- **发布到公网**
```

判定标准：**这个动作如果做错了，能不能撤销？** 不能撤销 → 必须问。
（可逆的、只读的 → 可以直接做。）

---

## 8. 能自动判的，别让人肉比对

> **凡是有明确「对/错」二元结果的检查，都应该写成脚本。**

| 人工检查 | 脚本化 |
|---|---|
| 挨个 curl 端点看有没有指标 | `verify-*.sh` 三态判定 |
| 肉眼比对 ServiceMonitor 标签 | `check-servicemonitor.sh` |
| 打开 dashboard 一个面板一个面板看 | `verify-dashboard.sh` 逐条跑查询 |
| 人工搜 IP / token | `scan-sensitive.py` |

脚本化的收益不只是省时间：**脚本的输出就是「通过条件」**，AI 能自己判断。
