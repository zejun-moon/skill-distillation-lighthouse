# 坑表：做技能仓这件事本身的坑

> 全部来自一次真实产出（2026-11-27 实测）。
> ✅ = 实测复现 · 📄 = 据源码/文档推断
> 排障先搜本文。

---

## 1. ✅ 扫描器把自己的规则和测试样本也扫了出来（自指误报）

- **现象**：`check_repo.py` 自检报 22 个问题，其中大部分在
  `tools/check_repo.py` 自己的规则定义行和 `tests/` 的样本行上
- **原因**：规则文件里写着被禁的关键词（某个内部账号前缀与真实姓名）；
  测试文件里必须写"真的 IP/真 token"才能验证扫描器
- **处理**：
  - 规则定义行加行内豁免：`# check_repo: allow —— 这是规则本身`
  - **测试样本改成运行时拼接**：
    ```python
    FAKE_IP = "192.168." + "2.31"
    FAKE_TOKEN = "gh" + "p_" + "abcdefghijklmnopqrstuvwxyz0123"
    ```
    → 源码里没有完整字面量，机器扫描器和 gitleaks 都不会误报
- **⚠️ 附带收益**：如果不这么改，**gitleaks 会把假 token 当成真密钥，CI 直接红**

## 2. ✅ 扫描器对真实清单命中 0 处（规则过窄 → 漏报，比误报危险）

- **现象**：拿**未脱敏**的真实 ServiceMonitor 清单喂扫描器 → **命中 0 处**
- **原因**：规则只覆盖了 IP / 域名 / 凭据，**漏了内部命名空间前缀**（`zzj-`）
- **处理**：补规则 `\bzzj-[a-z]` → 「内部命名空间前缀」，命中数变 2
- **教训**：**漏报没人会发现，误报天天打扰你。**
  → 每次改规则都跑**阳性对照**（拿未脱敏素材验），命中数为 0 就是扫描器坏了

## 3. ✅ IPv4 正则不校验八位组 → 版本号被当成 IP

- **现象**：`999.999.999.999` 被判为「真实 IPv4 地址」
- **原因**：正则只匹配形状，不校验取值范围
- **处理**：加 `_is_real_ipv4()`，八位组全部 ≤ 255 才算

## 4. ✅ 规则过宽误伤通用形态

- **现象**：`<svc>.<ns>.svc.cluster.local` 被判为「集群内 DNS 名」
- **原因**：K8s 通用 DNS 形态不泄露任何真实信息
- **处理**：**删掉这条规则**。真正的内部标识靠「ns 前缀 + 人名 + 内部域名」覆盖
- **教训**：规则的**意图**要写清楚。写不出意图的规则，早晚会误伤或漏报

## 5. ✅ 脚本里写死 uid / ns / 服务名 → 换环境就不能用

- **现象**：生成器里写死了真实 Grafana uid、真实 namespace、真实服务清单
- **原因**：直接照抄了本地的生成器
- **处理**：全部改成 CLI 参数：
  ```bash
  python3 gen-dashboard.py --datasource-uid <uid> --namespace <ns> \
      --services svc-a,svc-b --output dashboard.json
  ```
- **教训**：**技能仓里的脚本必须是"任何人都能跑"的**。
  写死的参数 = 泄露 + 不可复用，双输

## 6. ✅ 逐文件推送把历史打散成 31 个 commit

- **现象**：一次 `push_files`（git tree API）报 403 → 改用 `create_or_update_file` 逐文件推
  → 远端变成 **31 个 commit**，本地那个干净的 commit 丢了
- **原因**：Contents API 走用户 token（能写），但**没有批量接口**；
  git tree API 走 App 安装令牌，而新仓不在安装范围内
- **处理**：接受现状（内容对，历史碎），或让用户在 GitHub 网页加文件后用 git 推
- **教训**：**发布通道的能力要在动手前探明**。
  有批量接口就用批量接口；只有逐文件接口时，先想清楚历史碎掉能不能接受

## 7. ✅ 平台限制不是代码问题：`.github/workflows/*` 写不进去

- **现象**：推 `ci.yml` 报 `403 Resource not accessible by integration`
- **原因**：GitHub 对 `.github/workflows/*` 的写入强制要求 token 带 `workflow` scope；
  Contents API 和 git tree API **两条路都 403**
- **处理**：
  - 网页新建该文件粘贴内容（web UI 用会话 cookie，不受 scope 限制）
  - 或给连接器补 `workflow` scope
  - 或不做 GitHub CI，只保留本地自检
- **⚠️ 连带问题**：仓内文档写着「CI 还有 gitleaks」，文件却不在 → **文档与事实不一致**
  → 发布后必须**回读远端内容**校验，而不是相信"推送成功"的返回

## 8. ✅ 提交邮箱泄露到公共仓

- **现象**：公共仓的 commit 作者是 `名字 <真实邮箱>`
- **原因**：用用户 token 提交时，作者身份取自 GitHub 账号
- **处理**：`Settings → Emails → Keep my email addresses private`，
  然后**删仓重建**（无 star/issue 时重建无损）
- **教训**：**发布之前先想一遍「这个仓公开后，谁能看到什么」**。
  commit 元数据也是公开内容

## 9. ✅ 扫描器的规则改了但测试没改 → 扫描器静默退化

- **现象**：某次改了规则，测试还是绿的，但规则已经不匹配真实场景
- **原因**：测试只覆盖了"改之前"的行为
- **处理**：
  - 改规则 → **同时**改测试 → 补**阳性**样本（必须命中）
  - 放宽规则 → 补**阴性**样本（不得误报）
- **教训**：**测试跟着实现走，就失去了它的意义。**
  阳性对照（拿真实未脱敏素材跑）才是真正的验收

## 沉淀新坑的规矩

1. 按 `field-reports/TEMPLATE.md` 写一份脱敏报告
2. 逐条判断：会再遇到 → 写进本文；能自动检测 → 加进脚本；只是特例 → 只留报告
3. 在报告里标 `状态：promoted → pitfalls.md #N`
4. 更新 `CHANGELOG.md` 的 `[Unreleased]`
